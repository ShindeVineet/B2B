# Phase 6 — Smart Day-Wise Route Clustering

## Behavior

`clusterLeadsIntoDays(leads, dayCapacities, startPoint, mode)` is a pure function returning `days` (`day_index`, ordered `lead_ids`, `cluster_span_km`) and `unscheduled_lead_ids`. Zero-capacity days retain their calendar index. Insufficient capacity never extends the plan or discards overflow.

The first seed is farthest from the assigned store, or the northernmost lead with stable longitude/ID tie-breaking when no store exists. Batch membership is fixed by distance to the seed. Compact/Sequential chooses the next seed nearest to the preceding day's final optimized stop; Spread Coverage chooses the farthest remaining lead from the centroid of all clustered leads. Each batch gets nearest-neighbour ordering and up to two open-route 2-opt passes. Span is the exact maximum pairwise haversine distance.

Small pools use an isolated scan lookup; pools of 300 or more use an immutable 3-D unit-sphere k-d tree with active-pool filtering. Chord-distance ordering is equivalent to great-circle-distance ordering. Farthest-seed selection uses a linear scan. No provider calls, database writes or random choices occur inside the algorithm.

## Planner and publication

- **New plan → Auto-distribute & create draft plan** supports both modes and per-working-day capacities. Selected or automatically discovered leads already scheduled in a non-completed plan are not silently duplicated. Overflow remains assigned to the rep but unscheduled.
- Mode is persisted on `trip_assignments`. Changing the mode does not move visits; **Re-cluster** is a separate explicit action.
- As approved, initial distribution stays a draft preview. **Publish / republish** creates new snapshot versions with `cluster_span_km`, preserving the stored stop sequence. Existing snapshots are immutable and remain readable with null historical spans.
- The calendar computes current draft spans too. **Sparse day — leads are spread out** is informational, not a validation error.
- The rep's daily itinerary/navigation preserves the plan's sequence, rather than re-sorting away the clustering/2-opt/manual order. Custom routes remain separate.
- Calendar cards support drag-and-drop to another day and the existing Edit visit / lead action. Server-side working days, capacity, scope and completed-visit protections remain in force. Publish again to save changed route-history geometry.

## Re-cluster safety

The user approved this definition of unscheduled: mapped leads assigned to this rep, without a visit in any non-completed plan. Unscheduled overflow remains outside the calendar until capacity is available.

Re-cluster can include those unscheduled leads and/or explicitly selected visits from the current plan. Only these visits are modified. Unselected visits in draft plans reserve capacity. Days with unselected active/published visits or unselected visits in their latest published snapshot cannot receive redistributed leads. Explicit selection allows those visits to move; completed visits remain protected. No automatic extension, missed-visit event, or notification is generated by clustering.

If selected existing visits cannot fit into editable capacity, the transaction refuses the entire edit rather than losing their current schedule. Managers must extend the plan, adjust capacities or reduce their selection. Re-clustering uses each day's Phase 5 working-week override and capacity override. Writes are serialized per rep and use serializable transactions.

## Configuration

- `CLUSTER_SPARSE_THRESHOLD_KM`: positive distance, default **15**. The Plans screen also offers a threshold control saved in this browser.
- `CLUSTER_TWO_OPT_PASSES=0`: disable 2-opt for server-side clustering. Otherwise two passes are used. Pure-function callers can pass `{twoOptPasses: 0}` or `1`.

No new config table or extra schema fields were introduced.
